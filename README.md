# Persona Signal

제품팀이 카피, 가격, 기능 같은 작은 의사결정을 감으로만 하지 않도록, 타깃 페르소나 관점의 구조화된 사전 검토를 제공하는 pre-validation tool입니다.

Persona Signal은 "정답을 맞히는 AI"가 아닙니다. 출시 직전에 놓치기 쉬운 혼란, 신뢰 저하, 행동 저항, 구매자-사용자 불일치, 세그먼트별 거부 신호를 먼저 드러내는 의사결정 보조 도구입니다.

## 1. 한 줄 정의

**Persona Signal은 제품팀의 직감 기반 의사결정을 줄이기 위해, 타깃 페르소나 관점에서 카피·가격·기능안을 사전 검토해주는 persona-based decision support SaaS입니다.**

## 2. 해결하려는 문제

제품팀은 매주 수많은 작은 결정을 내립니다.

| 의사결정 | 실제로 자주 생기는 질문 |
| --- | --- |
| 랜딩 카피 | 이 헤드라인이 고객에게 바로 이해될까? |
| 가격 정책 | 이 가격이 합리적으로 느껴질까, 비싸게 느껴질까? |
| 기능 우선순위 | 이 기능이 정말 필요한가, 그냥 nice-to-have인가? |
| 온보딩/업그레이드 문구 | 전환을 만들까, 압박감과 CS 문의를 만들까? |
| 보안/신뢰 메시지 | 유저는 좋아해도 구매자나 승인권자가 막지 않을까? |

문제는 이런 결정이 자주 다음 방식으로 처리된다는 점입니다.

- 실험 없이 정해진다.
- 인터뷰 없이 내부 회의에서 결정된다.
- PM, 대표, 디자이너, 마케터의 경험과 감에 의존한다.
- 실제 타깃이 아니라 "우리 팀이 보기 좋은 문장"으로 판단된다.

초기 스타트업일수록 이 문제가 큽니다. 매번 리서치나 A/B 테스트를 할 리소스가 없고, 출시 속도는 빠르게 유지해야 하기 때문입니다.

Persona Signal은 이 빈틈을 메웁니다. 실제 유저 리서치를 대체하지 않고, 출시 전 의사결정에 들어가는 **가벼운 리스크 탐지 레이어**를 제공합니다.

## 3. 핵심 관점

Persona Signal의 가치는 "어떤 안이 이길지 예측"하는 데 있지 않습니다.

핵심 가치는 다음 질문에 답하는 데 있습니다.

- 누가 이 안을 이해하지 못할 수 있는가?
- 무엇 때문에 신뢰하지 않을 수 있는가?
- 좋아 보이지만 실제 행동으로 이어지지 않는 이유는 무엇인가?
- 평균 점수 뒤에 숨어 있는 강한 거부 세그먼트는 없는가?
- 실제 사용자와 구매자가 서로 다른 근거를 필요로 하지는 않는가?
- 지금 바로 고치면 리스크를 줄일 수 있는 문구나 구조는 무엇인가?

따라서 Persona Signal의 포지셔닝은 다음과 같습니다.

> "정답을 맞히는 도구"가 아니라 "틀릴 가능성을 먼저 드러내는 도구"

## 4. 핵심 사용자

Persona Signal은 다음 사용자를 1차 타깃으로 설계했습니다.

| 사용자 | 사용하는 순간 |
| --- | --- |
| 초기 스타트업 대표 | 출시 전 랜딩 메시지, 가격, 기능 방향을 빠르게 검토할 때 |
| PM | 기능 우선순위나 온보딩 문구를 배포 전에 점검할 때 |
| Product Designer | 유저 플로우 문구와 이해도를 검토할 때 |
| 마케터 | 랜딩 헤드라인, CTA, 업그레이드 메시지를 검토할 때 |
| 제품 오너 | 작은 의사결정이 누적되기 전에 리스크를 확인할 때 |

이들의 공통점은 명확합니다.

- 유저 리서치 리소스가 부족하다.
- 빠르게 배포해야 한다.
- 작은 의사결정이 전환율, 신뢰도, 제품 품질에 누적 영향을 준다.
- "그냥 ChatGPT에게 물어보기"보다 반복 가능한 의사결정 워크플로우가 필요하다.

## 5. 제품이 하는 일

Persona Signal은 하나의 결정 안건을 다음 구조로 평가합니다.

| 단계 | 내용 |
| --- | --- |
| Step 1 | 비교하기 또는 단일 검토하기를 선택합니다. |
| Step 2 | 카피/메시지, 가격/플랜, 기능 필요성 중 입력 타입을 선택합니다. |
| Step 3 | 제품 설명, 타깃 고객, 시장 유형, 사용/구매 맥락을 입력합니다. |
| Step 4 | 타깃 페르소나 조건과 표본 수를 선택합니다. |
| Step 5 | 페르소나별 반응, 세그먼트 차이, 핵심 리스크, 개선 제안을 확인합니다. |

지원 모드는 두 가지입니다.

| 모드 | 목적 |
| --- | --- |
| 비교하기 | A/B 중 어떤 안이 더 적합한지 판단합니다. |
| 검토하기 | 단일안이 출시 전 충분히 명확하고 설득력 있는지 점검합니다. |

지원 입력 타입은 MVP 기준 세 가지입니다.

| 입력 타입 | 예시 |
| --- | --- |
| 카피/메시지 | 슬로건, 헤드라인, CTA, 온보딩 문구, 기능 설명 |
| 가격/플랜 | 가격 정책, 플랜 구성, 무료/유료 경계, trial 설명 |
| 기능 필요성 | 기능 추가 여부, MVP 포함 여부, 우선순위 판단 |

## 6. 일반 AI 채팅과 다른 점

Persona Signal은 "AI에게 의견을 물어보는 화면"이 아닙니다. 제품 의사결정을 위해 구조화된 워크플로우입니다.

| 일반 AI 채팅 | Persona Signal |
| --- | --- |
| 한 번의 일반적인 의견을 생성합니다. | 여러 타깃 페르소나의 반응을 구조화해 비교합니다. |
| 질문자의 프롬프트 품질에 크게 의존합니다. | 제품 맥락, 타깃, 시장 유형, 사용 맥락을 고정 입력으로 받습니다. |
| 평균적인 조언에 머물기 쉽습니다. | 세그먼트별 차이와 숨은 리스크를 분리해 보여줍니다. |
| "더 좋게 써줘"로 끝나기 쉽습니다. | 어떤 리스크 때문에 어떻게 고쳐야 하는지 연결합니다. |
| 결과가 매번 산발적입니다. | 비교/검토 모드, 평가축, 요약 구조가 일관됩니다. |

심사 관점에서 중요한 차이는 이 부분입니다.

Persona Signal의 결과는 단순히 "B가 더 좋다"가 아닙니다. 예를 들어 다음처럼 의사결정 가능한 형태로 나옵니다.

> B안이 더 안전하지만, CTA 앞에 보안·데이터 보관·삭제 가능성에 대한 근거가 없으면 구매 승인 단계에서 막힐 가능성이 높다.

이것이 일반 챗봇 답변과 제품 워크플로우의 차이입니다.

## 7. 평가 모델

Persona Signal은 모든 안건을 공통 평가축과 타입별 추가 평가축으로 나눠 평가합니다.

### 공통 평가축

| 축 | 의미 | UI 기준 |
| --- | --- | --- |
| 이해도 | 무엇을 말하는지 바로 이해되는가 | 높을수록 좋음 |
| 신뢰도 | 과장 없이 믿을 만한가 | 높을수록 좋음 |
| 매력도 | 나에게 필요하거나 끌리는가 | 높을수록 좋음 |
| 수용도 | 거부감이나 행동 저항이 낮은가 | 높을수록 좋음 |
| 명확성 | 혼란이나 오해 가능성이 낮은가 | 높을수록 좋음 |

초기 버전에서는 `거부감`, `혼란도`처럼 낮을수록 좋은 축과 높을수록 좋은 축이 섞여 있었습니다. 현재는 읽는 사람이 직관적으로 이해할 수 있도록 모든 지표를 **높을수록 좋은 지표**로 통일했습니다.

내부적으로는 resistance와 confusionRisk를 수집한 뒤 다음처럼 변환합니다.

```text
수용도 = 6 - resistance
명확성 = 6 - confusionRisk
```

### 타입별 추가 평가축

| 입력 타입 | 추가 축 |
| --- | --- |
| 카피/메시지 | 기억성, 헷갈리는 표현, 설득 포인트 |
| 가격/플랜 | 체감가치, 부담도, 지불의향 |
| 기능 필요성 | 필요도, 긴급성, 대체재 인식 |

## 8. 페르소나 평가 방식

Persona Signal은 페르소나를 "비판적인 평가자"로 두지 않습니다. 실제 타깃 사용자처럼 반응하도록 설계했습니다.

각 페르소나는 다음 순서로 평가합니다.

| 순서 | 평가 내용 |
| --- | --- |
| 1 | 이 제품/안건이 나와 관련 있는지 relevance를 판단합니다. |
| 2 | 좋게 느낀 점을 최대 2개까지 기록합니다. 억지 긍정은 만들지 않습니다. |
| 3 | 걸리는 점을 최대 2개까지 기록합니다. |
| 4 | 기억에 남는 표현 또는 내용이 있는지 기록합니다. |
| 5 | 이해도, 신뢰도, 매력도, 행동 의향을 점수화합니다. |
| 6 | A/B 비교 모드에서는 단독 평가 후 마지막에만 선호안을 선택합니다. |

이 구조를 둔 이유는 명확합니다.

- 처음부터 A/B를 비교시키면 후광효과가 생길 수 있습니다.
- 단점만 찾게 하면 제품이 리스크 스캐너처럼 과도하게 비판적으로 동작합니다.
- 장점 2개를 강제하면 별로인 안에도 억지 긍정이 생길 수 있습니다.
- 따라서 "균형 반응 + 행동 의향 + 관련도 가중치" 구조가 필요합니다.

## 9. 관련도 가중치

모든 페르소나가 같은 수준으로 관련 있는 것은 아닙니다.

예를 들어 B2B SaaS 보안 메시지를 평가할 때, 실제 구매 승인권자와 일반 소비자를 같은 비중으로 보면 결과가 왜곡됩니다. 반대로 관련도가 낮은 사람을 완전히 제외하면 표본이 지나치게 예뻐질 수 있습니다.

그래서 Persona Signal은 relevance를 세 단계로 나누고 가중치를 적용합니다.

| 관련도 | 의미 | 가중치 |
| --- | --- | --- |
| high | 이 안건이 삶이나 업무에 직접 관련됨 | 1.0 |
| medium | 일부 관련은 있지만 완전한 타깃은 아님 | 0.7 |
| low | 원래 타깃과 거리가 있음 | 0.4 |

이 방식은 두 가지 극단을 피합니다.

- 낮은 관련도 반응을 완전히 무시해 결과가 과하게 좋아지는 문제
- 낮은 관련도 반응을 동일 비중으로 반영해 실제 타깃 결과가 흐려지는 문제

## 10. 페르소나 데이터와 샘플링

페르소나 데이터는 NVIDIA Nemotron-Personas-Korea를 기반으로 Supabase에 적재했습니다.

현재 데이터 구성은 다음과 같습니다.

| 항목 | 내용 |
| --- | --- |
| 데이터 규모 | 5,000개 한국어 페르소나 샘플 |
| 저장소 | Supabase PostgreSQL |
| 주요 구조화 필드 | 나이, 성별, 직업, 지역, 학력, 결혼 여부, 주거 형태 |
| 주요 서술형 필드 | 직업 페르소나, 가족 페르소나, 관심사, 목표, 문화적 배경, 스킬 |
| 원본 보존 | 전체 raw JSONB 보존 |

샘플링은 단순히 앞에서 자르지 않습니다.

현재 샘플링 로직은 다음 원칙을 따릅니다.

| 로직 | 이유 |
| --- | --- |
| 나이, 성별, 직군, 지역, 결혼 여부 필터 적용 | 사용자가 선택한 타깃을 최대한 보존하기 위해 |
| 직군 alias 매칭 | 원본 occupation 값이 UI 라벨과 정확히 일치하지 않는 문제를 줄이기 위해 |
| 나이 버킷 × 성별 층화 샘플링 | 25-42세를 선택했는데 20대 특정 성별만 나오는 쏠림을 줄이기 위해 |
| 후보 부족 시 점진적 fallback | 표본이 없어서 실행이 실패하는 상황을 줄이기 위해 |
| 직군 필터는 최대한 늦게 완화 | IT 종사자 선택 시 무직이 과도하게 섞이는 문제를 줄이기 위해 |

표본 수 옵션은 다음과 같습니다.

| 표본 수 | 권장 사용 |
| --- | --- |
| 10명 | 빠른 탐색 |
| 20명 | 기본 추천, 방향성 확인 |
| 30명 | 더 안정적인 검토 |
| 50명 | 비용과 시간이 더 들지만 깊은 스캔 |

## 11. 결과 화면에서 보여주는 것

결과 화면은 "차트가 많은 리포트"가 아니라 "바로 의사결정할 수 있는 브리프"로 설계했습니다.

상단에서 가장 먼저 보여주는 것은 다음입니다.

| 결과 요소 | 목적 |
| --- | --- |
| 추천 결론 | 어떤 안을 채택하거나 수정해야 하는지 즉시 파악 |
| 추천안 전문 | B가 좋다는 말이 아니라, 실제 어떤 문구/플랜/기능인지 크게 노출 |
| 핵심 리스크 | 출시 전에 가장 먼저 손봐야 할 문제 |
| 즉시 적용할 수정 방향 | 다음 작업으로 바로 이어지게 함 |

그 아래에는 다음 분석을 제공합니다.

| 분석 | 목적 |
| --- | --- |
| 공통 평가축 | 이해도, 신뢰도, 매력도, 수용도, 명확성을 한눈에 비교 |
| 타입별 심층 해석 | 가격이면 지불의향, 기능이면 필요도/긴급성 등 맥락별 판단 |
| 세그먼트별 차이 | 누가 특히 좋아하거나 거부하는지 확인 |
| 놓치기 쉬운 신호 | 평균 점수에 숨은 리스크를 별도 섹션으로 노출 |
| 페르소나별 반응 | 왜 그런 결과가 나왔는지 원문 반응으로 확인 |
| 개선안 생성 | 결과를 바탕으로 수정 후보 3개 생성 |

## 12. 놓치기 쉬운 신호

이 제품의 핵심 "딩!" 모먼트는 평균 점수보다 숨어 있는 리스크를 보여주는 데 있습니다.

Persona Signal은 다음 신호를 별도 섹션에서 감지합니다.

| 신호 | 의미 |
| --- | --- |
| 신뢰 갭 | 매력도는 높은데 신뢰가 낮아 행동으로 이어지지 않음 |
| 명확하지만 행동 안 함 | 이해는 되지만 필요성이나 긴급성이 부족함 |
| 비타깃 평균 희석 | 관련도 낮은 페르소나가 평균을 끌어내림 |
| 숨은 이탈 세그먼트 | 전체 평균은 괜찮지만 특정 세그먼트가 강하게 거부함 |
| 구매자-사용자 불일치 | 실제 사용자는 좋아하지만 구매자나 승인권자가 다른 근거를 원함 |
| 근소한 승리 | 승자는 있지만 바로 배포할 만큼 압도적이지 않음 |

이 섹션은 Persona Signal의 차별점을 가장 잘 보여줍니다.

제품팀에게 중요한 것은 단순 승자가 아니라, **왜 출시 후 실패할 수 있는지**입니다.

## 13. 개선안 생성

결과를 본 뒤 사용자는 개선안 생성 버튼을 누를 수 있습니다.

개선안 생성은 단순히 "더 좋은 문장 3개"를 만드는 기능이 아닙니다. 앞선 평가에서 발견된 리스크를 반영해 수정 후보를 만듭니다.

개선안 생성에 사용되는 정보는 다음과 같습니다.

| 입력 | 활용 |
| --- | --- |
| 제품 설명 | 문구가 제품 맥락에서 벗어나지 않게 함 |
| 타깃 고객 | 누구에게 설득되어야 하는지 유지 |
| 시장 유형 | B2B/B2C/B2B2C 맥락 반영 |
| 사용/구매 맥락 | 실제 행동 순간에 맞는 문구 생성 |
| 기존 A/B 또는 단일안 | 원문 대비 어떤 점을 고칠지 판단 |
| 핵심 우려 | 신뢰, 혼란, 가격 저항, 필요성 부족 등을 반영 |
| 추천 수정 방향 | 결과 화면의 인사이트를 실제 수정안으로 연결 |

각 개선안은 다음 항목을 포함합니다.

| 항목 | 의미 |
| --- | --- |
| 전략 | 어떤 방향으로 고쳤는지 |
| 개선된 결과물 | 실제로 사용할 수 있는 문구/플랜/기능안 |
| 근거 | 왜 이 방향이 더 나은지 |
| 개선 delta | 원문 대비 무엇이 좋아졌는지 |
| 남은 이슈 | 그래도 검증해야 할 부분 |

## 14. 데모 시나리오

데모는 "실제로 현업에서 넣을 법한 안건"처럼 느껴지도록 구성했습니다. 단순 예시가 아니라 제품팀 회의에서 실제로 나올 법한 의사결정 상황을 기반으로 했습니다.

| 데모 | 도메인 | 보여주는 핵심 가치 |
| --- | --- | --- |
| 보안이 막는 SaaS 랜딩 | B2B SaaS | 사용자 매력과 구매자 신뢰 리스크의 분리 |
| 다음 스프린트 기능 | B2B 기능 우선순위 | nice-to-have와 must-have의 차이 |
| D2C SaaS 가격표 | 커머스/구독 | 낮아 보이는 가격이 오히려 비용 불안을 만들 수 있음 |
| 무료체험 종료 모달 | 구독 전환 | 전환 압박과 CS 리스크의 균형 |
| 학부모 결제 앱 | 교육 | 사용자와 구매자가 다른 근거를 필요로 함 |
| 계좌 연결 첫 화면 | 핀테크 | 관심은 높지만 데이터 접근 불안이 행동을 막음 |

추천 시연 순서는 다음입니다.

1. **보안이 막는 SaaS 랜딩**: B2B에서 user와 buyer가 다르게 반응하는 장면을 보여줍니다.
2. **무료체험 종료 모달**: 전환율을 높이려는 문구가 오히려 압박감과 CS 리스크를 만들 수 있음을 보여줍니다.
3. **계좌 연결 첫 화면**: 명확하고 매력적인 메시지도 신뢰 장벽을 넘지 못하면 행동으로 이어지지 않음을 보여줍니다.

라이브 시뮬레이션도 가능하지만, 발표 안정성을 위해 데모 케이스는 미리 보기용으로 빠르게 로드할 수 있게 구성했습니다.

## 17. 비용과 지연시간

현재 구조는 페르소나 1명당 LLM 호출 1회, 마지막 요약 호출 1회를 사용합니다.

페르소나별 호출은 병렬화되어 있어 지연시간이 표본 수에 정비례하지는 않습니다. 하지만 표본 수가 커질수록 비용, rate limit 위험, 부분 실패 가능성은 증가합니다.

따라서 제품 사용 관점에서는 다음 전략이 현실적입니다.

| 상황 | 권장 표본 |

| 발표/출시 전 정밀 검토 | 30명 |
| 고신뢰 도메인 깊은 스캔 | 50명 |

## 18. 한계와 방어 논리

Persona Signal은 실제 유저 리서치나 A/B 테스트를 대체하지 않습니다.

명확한 한계는 다음과 같습니다.

- 합성 페르소나 반응은 실제 사용자 행동이 아닙니다.
- 점수는 통계적 진실이 아니라 방향성 신호로 읽어야 합니다.
- 작은 표본은 확정 판단보다 리스크 탐지에 적합합니다.
- LLM 출력은 실행마다 달라질 수 있습니다.
- 페르소나 데이터에는 데이터셋 편향이 포함될 수 있습니다.
- 관련도 가중치는 신호 품질을 높이지만 대표성을 증명하지는 않습니다.

하지만 이 한계가 제품의 약점만은 아닙니다. Persona Signal은 애초에 "정답 예측"이 아니라 "출시 전 리스크 탐지"로 포지셔닝되어 있기 때문입니다.

올바른 사용 방식은 다음입니다.

1. Persona Signal로 빠르게 리스크를 발견합니다.
2. 더 나은 후보안을 만듭니다.
3. 실제 유저 인터뷰, 분석 데이터, A/B 테스트로 최종 검증합니다.

## 19. 평가 관점에서 봐야 할 포인트

이 프로젝트의 완성도는 단순히 UI가 동작하는지보다, 문제 정의와 제품 구조가 일관되게 연결되어 있는지를 봐야 합니다.

| 평가 포인트 | 구현된 대응 |
| --- | --- |
| 문제가 실제로 자주 발생하는가 | 제품팀의 카피·가격·기능 의사결정에 집중 |
| 일반 AI 채팅과 차별화되는가 | 페르소나 샘플링, 구조화 평가축, 세그먼트 해석, 개선안 생성 |
| 결과가 행동으로 이어지는가 | 추천안 전문, 핵심 리스크, 수정 방향, 개선안 3개 생성 |
| 신뢰성 리스크를 인정하는가 | 예측이 아니라 리스크 탐지로 명시, 한계와 주의 신호 제공 |
| 데모가 현업형인가 | B2B SaaS, 커머스/구독, 교육, 핀테크 시나리오 구성 |
| 기술적으로 완결되어 있는가 | Supabase 데이터, Next.js API, OpenAI 평가/요약/개선 파이프라인 구현 |

## 20. 왜 이 프로젝트가 중요한가

제품의 실패는 항상 큰 전략 실패에서만 오지 않습니다.

작은 문구 하나, 애매한 가격 설명, 불필요한 기능, 불안한 온보딩 문구가 쌓여 사용자의 이해와 신뢰를 떨어뜨립니다.

대부분의 초기 팀은 모든 의사결정마다 리서치를 할 수 없습니다. 그렇다고 모든 결정을 내부 감으로만 처리하는 것도 위험합니다.

Persona Signal은 이 중간 지점을 노립니다.

빠르게 결정해야 하지만, 완전히 감으로만 결정하고 싶지는 않은 팀을 위한 사전 검토 도구입니다.

이 프로젝트의 핵심 주장은 다음입니다.

> 제품팀은 모든 작은 결정을 실험할 수는 없지만, 모든 작은 결정을 감으로만 할 필요도 없다.

Persona Signal은 그 사이에 들어가는 현실적인 decision support layer입니다.

## 22. 결론

Persona Signal은 "AI로 유저인 척 의견을 말하게 하는 도구"가 아닙니다.

제품팀이 출시 직전에 자주 내리는 작은 결정을 더 구조적으로 검토하게 만드는 도구입니다.

이 프로젝트가 보여주는 핵심은 세 가지입니다.

1. 제품팀의 반복적인 의사결정 문제를 명확히 잡았다.
2. 일반 AI 채팅이 아니라 decision workflow로 제품화했다.
3. 결과를 점수표에서 끝내지 않고 리스크 발견과 수정 행동으로 연결했다.

그래서 Persona Signal은 해커톤 데모로 끝나는 아이디어가 아니라, 초기 제품팀이 실제로 "출시 전 한 번 돌려보는 습관"을 만들 수 있는 제품 방향성을 가집니다.
